# Image Flow 0.1 알파 구현·실제 생성 검증

검증: 2026-09-19~20 KST. 대상: 이 저장소의 제품 앱 `dist/ImageFlow.app`. 환경: Apple Silicon, macOS 27.2, Swift 6.4. macOS 14 deployment target.

## 구현 범위

SwiftUI의 프로젝트 사이드바, 배치별 이미지 보드, 공통 참조·요청 작성기, 2~4개 비교와 함께 확대, 후보 표시, 원본 연결 수정, 인스펙터, 이미지·manifest 일괄 내보내기를 구현했다. 큐는 프로젝트와 창 전체에서 공유하며 동시 작업 상한 3개, 절전 1개, 앱 전체 전송 간격 30~120초를 적용한다. 작업 입력을 등록 시점에 복사하므로 초안 수정과 실행 작업이 분리된다.

SwiftData에는 프로젝트·자산 목록을, 별도 atomic JSON journal에는 원격 요청 상태·대화 식별자·다음 전송 시각을 저장한다. 파일은 관리 폴더에 보존하고 생성 결과의 저장 영수증으로 메타데이터 저장 중단을 복구한다. 복구 기록은 이미 사용자가 변경한 후보 표시·이름을 덮어쓰지 않는다. 전송 이후 중단은 `needsReview`가 되며 자동 재전송하지 않는다.

네이티브 라이브러리에 웹뷰를 상시 붙이지 않는다. 세션 확인용 웹뷰는 숨김 상태에서 로그인을 확인한 뒤 해제하고, 작업용 웹뷰는 작업 종료 시 해제한다. 썸네일은 640px로 생성하고 메모리 캐시에 비용·개수 제한을 둔다.

## 실제 계정 검증

사용자가 앱 전용 연결 창에서 직접 로그인했다. 로그인 완료 이후 실제 이미지 생성 테스트를 승인한 범위에서 아래 작업을 진행했다. 대화 5개에서 이미지 5개를 저장했다.

| 경로 | 결과 | 관찰 |
| --- | --- | --- |
| 참조 없이 생성 | 1개 저장 | 파란 도자기 화병, 1254×1254 |
| 기존 이미지 수정 | 1개 저장 | 생성본을 실제 첨부해 테라코타 색상으로 수정, 1254×1254, parent 연결 유지 |
| 참조 2장을 공통으로 쓰는 배치 | 3개 저장 | 두 화병을 함께 배치하는 요청 3건. 1374×1145 1개, 1254×1254 2개 |
| 기존 대화 복구 | 성공 | 첫 생성의 결과 감지 수정 후 재실행, 원래 대화에서 회수. 새 요청을 보내지 않음 |
| 일괄 내보내기 | 5개 모두 통과 | manifest의 실제 파일명과 파일별 SHA-256이 저장 자산의 해시와 일치 |
| 앱 재실행 | 성공 | 로그인·완료 작업 5개·결과 5개·후보 표시 1개·마지막 프로젝트 유지, 추가 생성 없음 |
| 네이티브 비교 화면 | 표시 확인 | 실제 원본·수정본을 나란히 표시, 스크린샷으로 확인 |

이 배치는 다중 첨부와 큐 처리의 통합 검증이다. 서버 동시성 상한이나 3개 워커가 동시에 끝까지 실행되는 최대 부하를 증명하지 않는다. 비교·생성 테스트는 개발용 로컬 명령으로 앱의 같은 저장소·엔진·화면을 호출했다. 모든 버튼을 자동 클릭하는 종단간 UI 테스트는 아니다.

## 실서비스 통합에서 발견·수정한 차이

현재 관찰한 ChatGPT 이미지 응답에는 `[data-message-author-role="assistant"]` 래퍼가 없었다. 최초 어댑터는 이 래퍼를 전제로 해 이미 생성된 이미지를 인식하지 못했다. 실제 DOM을 확인해 다음 규칙으로 수정했다.

- assistant 영역 또는 명시적인 생성 이미지 alt 표식을 가진 이미지로 제한한다.
- 사용자 메시지와 작성기 내부의 참조 이미지는 제외한다.
- 저장 이미지 URL 패턴과 파일 ID로 후보를 식별·중복 제거한다.
- 새 파일, 실제 크기, 로딩 완료, 생성 중지 상태, 5초 안정성을 함께 확인한다. 감지한 결과 중 아직 로딩 중인 이미지가 있으면 완료를 보류한다.
- 전송 의도와 간격을 먼저 기록하고, 대화 ID를 발견하는 즉시 저장한다.

실제 이미지 바이트는 인증된 페이지 문맥의 fetch → Blob → Base64 → Swift Data 경로로 수집했다. **이 경로는 스트리밍 다운로드가 아니다.** 현재 앱이 화면의 결과 URL에서 제공받은 이미지 파일을 그대로 저장한다는 의미이며, 서비스에 더 높은 해상도의 별도 다운로드 자산이 있는지까지 비교한 것은 아니다. 제품에서 WKDownload 인증 다운로드를 사용한다는 주장은 하지 않는다.

## 자동 테스트

`swift test`: **12개 통과, 실패 0**.

작업 입력 스냅샷, 배치 경계, 모든 제출 이후 상태의 복구, 제출 이전 복구, 저장된 전송 간격, 손상 journal 차단, 대화 URL 검증, 이미지·영수증 복구, HTML 저장 거절, 원본 이동 후 참조 유지, 내보내기 파일 매핑·바이트, 후보 표시를 보존하는 복구를 검증한다. 이 중 어댑터 테스트는 실제 제품 JavaScript를 로컬 WKWebView의 합성 DOM에서 실행해 현재의 래퍼 없는 생성 이미지, 사용자 참조 제외, 파일 중복 제거를 확인한다.

구현 전 검증 패키지의 11개 단위·7개 별도 프로세스 SIGKILL·18개 WebKit/DOM 검사는 [PREFLIGHT_REPORT.md](PREFLIGHT_REPORT.md)의 별도 증거다. 이를 제품 자체의 전체 강제 종료 테스트 수로 합산하지 않는다.

증거 요약: [alpha-validation.json](evidence/alpha-validation.json). 상세 개발 로그는 Git에서 제외된 `.runtime/tests.log`, `build.log`, `export-validation.json`에 있다. 계정 화면·사이드바가 포함된 진단 캡처는 공개 문서에 복사하지 않는다.

## 자원 측정과 남은 범위

재실행 후 유휴 상태에서 작업 웹뷰 0개, 세션 확인 웹뷰 해제를 확인했다. 앱 호스트 프로세스 RSS의 한 시점 관찰값은 약 147 MiB, CPU 표시는 0.0%였다. **WebKit 보조 프로세스를 합산한 총량이나 장시간 평균이 아니다.** 경쟁 프로젝트 대비 자원 사용 우위를 입증한 벤치마크로 사용하지 않는다.

현재는 실제 생성 흐름이 연결된 로컬 알파다. 다음 항목은 후속 구현·검증 범위다.

- 이름 붙인 레시피 관리, 변경점 비교, 삭제·실행 취소, 더 세밀한 다중 선택과 빈 검색 결과 UX.
- 수천 장 라이브러리, 장시간 배치, 잠자기·깨우기, 세션 만료·제한의 실서비스 시나리오, 여러 OS·로그인 방식.
- 스트리밍 다운로드 및 전체 WebKit 프로세스까지 포함하는 반복 성능 측정과 경쟁 앱 비교.
- 앱 아이콘·접근성·메뉴·키보드 흐름의 마감, 배포 서명·공증·업데이트.
- 공개 배포 전 서비스 조건 및 DOM 변경 대응 절차 확인.

이번 실행에 추가 권한 요청은 필요하지 않았다. 실제 계정 로그인은 사용자 직접 조작으로 완료했다.
